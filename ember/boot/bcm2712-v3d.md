# BCM2712 V3D identification

The native `bcmv3d` ACPI observer prepares the hardware boundary for an
EmberBSD V3D driver. It discovers the GPU described by the existing CM5
UEFI, queries its clock and reset state, and only attempts identification
when the observed prerequisites are ready. This is an EmberBSD implementation;
no DRM device, command submission, display output or acceleration is provided.

## Resources and ownership

The observer matches `BCM2712` with compatible ID `BCM2850`. It requires
`_STA=0x0f`, `_CCA=0` and these exact initial `_CRS` memory resources:

| Block | Physical address | Size |
| --- | --- | --- |
| HUB | `0x1002000000` | `0x4000` |
| CORE0 | `0x1002008000` | `0x6000` |
| SMS | `0x1002030800` | `0x700` |

Unsupported resources stop before mapping. Other GPU0 resources describe the
display path; this observer neither maps them nor establishes interrupts.
The existing `bcmpmwdog` driver owns PM00. A read-only accessor uses that
owner's mapped `PM_GRAFX2712` register at `+0x304`; no second PM mapping is
created. An absent or insufficiently sized owner prevents GPU access.

A one-shot autoconfiguration finalizer runs after the PM and mailbox providers.
The [bounded mailbox transport](bcmmbox-transactions.md) requests only firmware
GET_CLOCKSTATE and GET_CLOCKRATE for V3D clock ID 5.
Each validated clock result is reported immediately. PM is queried independently,
including after a clock error; the first error and its stage remain decisive.
An unqueried value differs from a valid zero. Transport failure and rejected
response framing have separate diagnostics; only a completed transport prints
its eight reply words. A failed property stops further mailbox queries and
still prevents every GPU mapping. The observer validates message size,
success code, tag, payload size, response
length, echoed clock ID and terminator before using a value. It changes no
clock, frequency, voltage, power policy, reset or SMS register.

## Identification gate

Clock state must be exactly 1 (present and enabled), the configured rate must
be nonzero, and PM `V3DRSTN` bit 6 must be set. The observer then maps SMS and
requires two identical complete REE/TEE snapshots. Each register must have
STATE=IDLE, equal OLD_MODE/NEW_MODE fields, and no other set bits. Mode values
remain opaque; they do not establish a security mode or permission to submit
work. A power-off, lock, transition, interrupt, nonzero state or fault ends
the observation before HUB/core mapping.

Only after these checks does it read HUB IDENT1/IDENT3, CORE0 IDENT0 and
MMU_DEBUG. IDENT1 must describe V3D 7.1 with one core. Unexpected values are
errors; there is no expected-ID fallback. All reads use `bus_space_peek_4`
and all acquired GPU mappings are released on every return path.

These are observations, not an ownership lease against firmware changes.
Fault-aware reads handle bus faults but cannot bound a stalled MMIO transaction.
A successful ID does not establish DMA addresses, cache coherency, MMU tables,
interrupts, scheduler recovery, Vulkan/GL support or Mesa compatibility.
In particular, `_CCA=0` requires explicit CPU/GPU cache synchronization in a
future DMA implementation.

## Checks

Run the actual-source host contract:

```sh
sh ember/tools/bcm2712-v3d-contract.sh "$PWD"
CFLAGS='-fsanitize=address,undefined -fno-sanitize-recover=all' \
    sh ember/tools/bcm2712-v3d-contract.sh "$PWD"
```

The harness substitutes host services, executes the production driver and PM
accessor, and checks malformed firmware replies, unavailable providers,
unready clocks/reset/SMS, rejected ACPI resources, faulting reads, failed
mappings, cleanup and one-shot finalization. Its fake I/O does not establish
physical register availability. For cross execution, set `CC`, `CFLAGS` and
`TEST_RUNNER` to an executable that accepts the target binary path. Set
`V3D_OUTPUT` to retain it; `V3D_COMPILE_ONLY=1` suppresses execution.

On 2026-10-09, all 186 cases passed on macOS with ASan/UBSan; nine compiled
causal mutants were rejected. The contract requires exactly two GET requests,
rejects GET_CLOCK_MEASURED without transport, and checks that zero is not
accepted as the echoed ID of either required clock property.
The SMS cases cover every old/new mode pair in both banks, every non-mode
bit, changes between samples, and the observed REE=0/TEE=0x50 handoff.
The GCC16 static cross build also passed all 186 cases on physical CM5 CPU.
These tests substitute hardware services; they do not access physical V3D.

Build the complete `EMBER64` kernel and matched modules from a clean commit
using the [cross-build guide](cross-build.md). Preserve the installed boot
path and a recoverable previous bundle before installing on a board.
Physical results must identify the board, firmware, source revision and
kernel hash separately from these software checks.

## Physical CM5 result

The complete GCC16 EMBER64 kernel and four matched modules from
`ec898852cdcb763ea494ccb1ca85eebaae8868d8` booted on physical Compute Module 5
Rev 1.0, BCM2712 D0, 4 GiB, on Waveshare CM5-NANO-B on 2026-10-09.
Kernel SHA256:
`52b1660d53a5cecd097a58878b8172f595e579f3b3468137b1905820fee58f6f`.
The existing UEFI/ACPI path was retained; its exact firmware source revision
is unknown. The kernel revision and hash matched after reboot. The Ethernet
and button modules loaded, and SSH over Wi-Fi remained usable. This short
boot check does not repeat Ethernet data-path or physical-button acceptance.

```text
clock5 state=0x1
clock5 rate=500000000 Hz
PM_GRAFX2712=0x1040
SMS REE=0 TEE=0x50
V3D 7.1 IDENT1=0x81117 IDENT3=0x20a10 CORE_IDENT0=0x7443356 MMU_DEBUG=0x20804664
```

This establishes physical V3D 7.1 identification with one core and readable
HUB/CORE/MMU registers. Both SMS observations matched with IDLE state and
unchanged mode fields. No GPU command, power/reset/SMS write or DMA mapping
was performed. The observed rate is configured, not a measured frequency.
The source boot log SHA256 is
`70c1f4651068c24a55daf6ed2fc933c25836b25f6be52f97d8182c49f1d9645c`.
DMA/MMU operation, interrupts, recovery, Mesa rendering and an accelerated
Wayland session remain unverified.

The separate opt-in [reset takeover probe](bcm2712-v3d-takeover.md#physical-cm5-acceptance)
has since completed SMS and PM reset on the same physical CM5.
The ordinary observer remains passive; that experiment adds no DMA or rendering.

Two earlier failures explain the prerequisites. Kernel `91b9d4eeb3f`
rejected GET_CLOCK_MEASURED because its reply echoed ID0 instead of ID5.
That optional property is not part of Linux's firmware-clock V3D setup
and is no longer requested; the malformed reply is never accepted.
Kernel `4de4756b519` reached SMS but rejected TEE `0x50` with its old
whole-register-zero test. The field-based correction accepts only IDLE,
equal opaque modes and two stable samples. It does not special-case `0x50`
or write SMS to force readiness.

## Hardware references

Register facts and initialization order were reviewed against Raspberry Pi
Linux [`43c132e8863c3bff3647033b6a7d2bf87b15501c`](https://github.com/raspberrypi/linux/tree/43c132e8863c3bff3647033b6a7d2bf87b15501c):
[`v3d_drv.c`](https://github.com/raspberrypi/linux/blob/43c132e8863c3bff3647033b6a7d2bf87b15501c/drivers/gpu/drm/v3d/v3d_drv.c),
[`v3d_regs.h`](https://github.com/raspberrypi/linux/blob/43c132e8863c3bff3647033b6a7d2bf87b15501c/drivers/gpu/drm/v3d/v3d_regs.h)
and [`bcm2835-power.c`](https://github.com/raspberrypi/linux/blob/43c132e8863c3bff3647033b6a7d2bf87b15501c/drivers/pmdomain/bcm/bcm2835-power.c),
with firmware-clock operations in
[`clk-raspberrypi.c`](https://github.com/raspberrypi/linux/blob/43c132e8863c3bff3647033b6a7d2bf87b15501c/drivers/clk/bcm/clk-raspberrypi.c).
Linux actively prepares clock/reset and SMS before reading the ID. This
passive observer deliberately stops when firmware has not done that work;
mailbox domain 11 is not assumed to implement the BCM2712 power sequence.
Before Linux's
[`SMS reset fix`](https://github.com/raspberrypi/linux/commit/1bdf2ccc351ce73ec5fcc0fa82eb6959b30f34c7),
the driver read MMU/HUB identification after clock enable without SMS writes.
The fix concerns reset and unload/reload handling. This observation path
does not provide those lifecycle operations.

The ACPI layout matches the recorded CM5 DSDT and the
[eotics EDK2 platform sources](https://github.com/eotics-com/edk2-platforms/tree/c4b5d05de1f2ef633bdb4c175b5c118fcb2666ed).
This source correspondence does not identify the installed firmware binary.
The UEFI IRQ labels disagree with Linux's binding order: Linux uses HUB 282,
CORE 281. The observer uses neither; a future interrupt driver must resolve
that boundary rather than copy the labels.

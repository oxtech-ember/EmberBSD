# YS-M33 copied environment for a one-shot trial

[Cable write stage](ys-m33-a133-cable-stage.md) ·
[Persistent recovery](ys-m33-a133-recovery-protection.md) ·
[Backup and recovery](ys-m33-a133-backup-recovery.md)

`A133Recovery.trial` in the [existing environment preparer](../../a133-recovery-env.rb)
constructs private 128 KiB copies for one normal boot with recovery selected
before kernel handoff. It performs no host file creation, device I/O, unlock,
reboot or confirmation. It is not connected to the cable write coordinator.

## Input and outputs

```ruby
require_relative '../tools/a133-recovery-env'

# Use this tablet's freshly verified original prefix, not its protected env.
copies = A133Recovery.trial(original_env.byteslice(0, 131072))
trial_prefix = copies.fetch(:trial_env)
expected_rearmed_prefix = copies.fetch(:rearmed_env)
```

The input must have the same CRC32 and factory boot profile required by
`A133Recovery.protect`. Existing hook/recovery helpers are refused, including
empty values. Existing `ember_trial_rearm` or `ember_trial_save` is also refused.
Foreign scripts, invalid size/CRC, duplicate variables and insufficient capacity
stop preparation. The original is copied; the returned Hash and both byte strings
are frozen. Errors carry bounded reasons without input contents or nested causes.

Both outputs preserve unrelated values, opaque values, empty values, leading-entry format and padding.
The hook profile changes boot_normal and preserves bootcmd and boot_android.
The direct profile changes bootcmd and preserves both factory image scripts.
Reversing each profile's additions and boot-selection change must restore every original byte. The original env tail
is outside this prefix-only API; a future guarded transition must retain and
verify the entire env partition, not only these outputs.

## Proposed boot sequence

For the hook profile, the trial prefix adds recovery and trial helpers, then sets:

```text
boot_normal=run ember_trial_rearm ember_trial_save boot_android
ember_trial_rearm=setenv boot_normal run ember_recovery_once
ember_trial_save=saveenv
```

The first stage selects persistent recovery in RAM. The second saves that state.
Only a successful save permits the third stage to call the unchanged factory
boot_android script. A single `run` list aborts at a failing variable; commands
separated by semicolons can continue after a failure. This distinction is stated
in the [upstream command-line contract](https://docs.u-boot.org/en/latest/usage/cmdline.html#general-rules).

`rearmed_env` encodes the proposed saved state: boot_normal becomes
`run ember_recovery_once`; the two unused trial helpers remain. When the
inspected bootcmd reaches that saved boot_normal entry, it selects recovery
under the stated parser contract. This is a byte
prediction, not a readback or evidence of factory saveenv formatting/durability.
No assumption that a later reset automatically removes the helpers is made.

The direct profile requires the exact factory `setargs_nand` template pinned by `DIRECT_SETARGS` in the implementation.
The direct trial does not use `boot_android`. It uses separate load and boot helpers:

```text
bootcmd=run ember_trial_rearm ember_trial_save setargs_nand ember_trial_load ember_trial_boot
ember_trial_rearm=setenv bootcmd run setargs_nand ember_recovery_once
ember_trial_save=saveenv
ember_trial_load=sunxi_flash read 45000000 boot
ember_trial_boot=bootm 45000000
```

Its saved `bootcmd` is `run setargs_nand ember_recovery_once`.
Recovery selects the control FDT, selects USB device mode, and runs the retained `boot_recovery` script.
The trial keeps image loading and kernel handoff in separate `run` variables.
Thus a reported load failure cannot continue into `bootm` under the stated parser contract.
The generated bytes do not prove vendor execution or successful persistence.

The existing [first-boot guard](../../../boot/a133-firstboot-guard.sh) requests a clean
reset after an unconfirmed running kernel. Its marker must be installed and
armed by a future guarded trial stage. Kernel hangs require the independently
verified watchdog path; generating these env copies does not establish either.
Normal-boot release must follow authenticated, release-bound confirmation in a
separate stage. Removing a marker alone must not certify installation readiness.

The optional [rc hook](../../../boot/a133-firstboot-guard.rc) installs as
`/etc/rc.d/ember_firstboot_guard` with mode0555. Install the guard library as
`/usr/libexec/a133-firstboot-guard.sh` with mode0444. Both belong to root.
Enable `ember_firstboot_guard=YES` only in the selected first-boot image profile.
The default is disabled; an already loaded YES is preserved.

The hook orders after critical local mounts and `mcu7502_keepalive`, before
`random_seed`. Missing or symlinked markers do nothing. A pending marker requires
the readable guard library and a running MCU service, then starts one120-second
background guard. The image must supply a writable `/var/log` and root-owned
marker directory. The hook does not create the marker, arm recovery, stop the
MCU service, write boot/env partitions or establish watchdog qualification.

## Build MCU helpers for vendor Linux recovery

Run the [host build script](../../mcu7502-linux-build.sh) with the selected
SDK host prefix and a new output directory:

```sh
"$SDK_HOST_PREFIX/bin/mksh" ember/tools/mcu7502-linux-build.sh \
    "$SDK_HOST_PREFIX" /work/recovery-mcu
```

The script builds three freestanding Linux AArch64 executables with Clang and
LLD. Each acts once on the recovery driver's `/dev/mcu_7502`. All require
MCU version `0x170307` and a status in the range 0 through 255. Each control
ioctl must return 7. Each successful control is followed by a 100 ms pause.

| Executable | Control sequence |
| --- | --- |
| `mcu-arm60` | Set the period to 60 seconds, enable, then set the period to 60 seconds again. |
| `mcu-feed60` | Set the period to 60 seconds once. |
| `mcu-disable` | Disable once. |

On success, stdout contains seven little-endian 64-bit words. They hold the
version, initial status, first control result, enable result, second period
result, final status and completion marker `0xc360`. Unused slots are zero.
The caller must check exit status zero and the complete 56-byte result.
The recovery caller owns feed scheduling and watchdog qualification.

Use the [recovery MCU control](../../a133-recovery-mcu.rb) from the caller
that already verified the recovery layout. Supply the model, CID, USB serial
and boot ID from that phase. Select the trusted executable and digest for
the requested action together. Feed and disable have the same ACK layout.

```ruby
mcu = A133Recovery::McuControl.new(adb: adb, serial: serial, cid: cid, model: model)
mcu.run(action: 'arm', helper: arm_path, sha256: arm_digest, boot_id: recovery_boot_id)
```

Each call requires USB recovery with root and shell v2. Arm requires unlocked
orange recovery. Feed and disable also accept locked green recovery. The
shell stages the checked helper in a fresh mode-0700 directory under a
root-owned RAM-backed `/tmp`, verifies its SHA-256 and checks the pinned
identity before and after execution. A pre-existing action directory causes
the call to fail. Success returns `true` after exit zero and ACK validation.
If `McuControl::Invalid#action_attempted` is true, delivery may already have
occurred. Resolve that outcome before issuing another action.

Vendor recovery reported a root-owned, mode-0775 `/tmp` on tmpfs through
`stat -c %u:%a .` and `stat -f -c %t .`. The shell enters the fixed
`/tmp/ember-mcu7502` directory, checks its filesystem and requires UID 0
and mode 0700. It compares the device and inode of its current directory
with the named entry using `stat -c %d:%i:%u:%a` without symlink
dereference. All helper writes and cleanup then use relative paths within
that pinned directory. The outer private directory persists in RAM for
subsequent actions.

One YS-M33 vendor recovery run verified all three actions through this API.
Each returned exit zero and a valid 56-byte ACK. The recovery initially ran
adbd as UID 2000. The caller requested `adb root` once, then verified UID 0
with the same USB serial, CID and boot ID before starting the actions.
USB re-enumeration required restoring host access to that device node.
The test made no environment or eMMC writes. It did not measure watchdog
expiry or exercise the complete trial coordinator.
[AOSP Android 10 toybox stat](https://android.googlesource.com/platform/external/toybox/+/android-10.0.0_r1/toys/other/stat.c)

## Prepare normal boot after native acceptance

`A133Recovery::Policy#normal_boot_env(actual_env)` prepares a full environment
from the saved rearmed state. Construct the policy with this tablet's verified
backup and original full environment, as for the existing recovery transitions.
The method performs no I/O and does not confirm native acceptance.

It verifies the full partition length, CRC, original tail and exact rearmed
variables. It uses the existing direct-profile runtime export matcher.
It restores only the factory boot selector: `bootcmd` for the direct profile,
or `boot_normal` for the hook profile. Other entries, inert helpers, opaque
values and formatting remain. The result is a new frozen byte string.
Original, unknown and already released states are refused.

The caller must authenticate the native boot and bind acceptance to the device
and release before writing. It must persist intent, preserve the original
environment and verify the complete partition after writing the prefix.
This method does not rearm recovery on later boots or request a reboot.
The explicit [native postboot stage](ys-m33-a133-cable-stage.md#native-confirmation-and-normal-release) calls this method.
The cable write stage still stops in protected recovery.

## Host validation and remaining gates

```sh
ruby ember/tools/a133-trial-env-test.rb
ruby ember/tools/a133-native-normal-env-test.rb
ruby ember/tools/a133-recovery-direct-protect-test.rb
ruby ember/tools/a133-recovery-env-test.rb
ruby ember/tools/a133-recovery-protect-test.rb
ruby ember/tools/a133-unlock-env-test.rb
ruby ember/tools/a133-env-edit-test.rb
sh ember/tools/a133-firstboot-guard-test.sh
python3 ember/tools/a133-firstboot-rc-test.py
```

The new test independently encodes expected binary env copies and checks all
four padding/leading-entry variants, input preservation, reversal and refusals.
It does not execute or emulate U-Boot. Existing environment/first-boot guard
tests remain separate contracts. No shell model is presented as vendor execution.

All outputs carry `installation_ready: false`. Before a physical trial, verify
images and retained recovery, pin the release/device/evidence, persist trial
intent before any env write/reboot, verify full write readback, install a bound
confirmation marker and test rearm/save failure behavior on the actual loader.
Host interruption, unknown/partial env, failed save, cold power loss and lost
host connectivity need explicit recovery policies. The current cable stage
continues to accept only its original/protected states and never adopts these
new states automatically. The explicit native postboot API can confirm a caller-accepted native boot and
release normal boot. Trial arming, restoration and fleet readiness remain
unimplemented by this preparer.


The standalone image Client keeps its existing prefix policy and can accept a
rearmed prefix with inert helpers. The stronger exact original/protected env
restriction described above belongs to the composed A133Cable flow.

Calls require a trusted Ruby process and ordinary byte inputs. They do not isolate hostile in-process code.

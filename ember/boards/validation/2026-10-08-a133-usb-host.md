# YS-M33 A133 USB-A host validation

Physical YS-M33 desktop tablet, A133, 1 GiB RAM, existing vendor boot chain,
NetBSD 11/aarch64 userland. Board and panel revisions remain unrecorded.
Source commits `a4969e57ab1e`, `6e877a3d7860` and `2db8e449fd25` add the
USB1 resource adapter, legacy GPIO decoding and hub/downstream power gates
to the retained A133 audio/touch/eMMC kernel source branch.

## Cause and adaptation

The original vendor tree used unsupported EHCI/OHCI compatible strings,
legacy clock cells, and a shared EHCI register tuple for the OHCI node.
The early adapter translates verified USB1 resources to generic EHCI/OHCI,
the existing A100 CCU provider and an A100 USB PHY. OHCI uses its own
register base at `0x05200400`, rather than the legacy shared base.
USB0/USB-C resources are not converted.

Controller attachment alone did not enumerate the external device. The
internal four-port hub and downstream power gates were disabled. The
adapter validates the vendor power descriptors, then the PHY owns PF0,
PF2, PF3, PF4 and PF5. GPIO cell 3 in the seven-cell vendor binding is a
mux selection, not a native active-low flag; the GPIO decoder now distinguishes
these formats. Other GPIO banks and the PF6 audio amplifier pin are retained.

Mainline Linux A100 DTS provides the generic host/PHY register and CCU
binding reference. The A133 vendor tree and physical readback determine
this board's IRQs and power GPIOs; shared SoC naming alone is not proof.

## Checks and physical result

The new FDT contract first failed to find a generic host, then passed the
resource conversion, OHCI base, VBUS guards, hub power GPIOs and repeat call.
It also passed on the full inspected vendor tree. The GPIO contract first
failed without the decoder, then passed native polarity, legacy output and
malformed-cell checks. Existing A133 audio, touch, MMC and SDIO portable
contracts passed before the initial USB build. The changed production
sources compiled and linked natively in NetBSD 11/aarch64.

After ordinary eMMC reboot with the final kernel, `usbdevs -v` and kernel
messages showed EHCI/OHCI root hubs, a high-speed vendor `1a40` four-port
hub, and ArduPilot `1209:5740` Pixhawk6X on hub port 3. The flight controller
briefly enumerated its Auterion bootloader, then re-enumerated as the normal
ArduPilot device with `umodem0`/`ucom0` and `umodem1`/`ucom1`. Its USB serial
number is intentionally omitted. No post-boot MMIO power probe was required.

Before and after the final reboot, a separately built, unprivileged read-only MAVLink
application received a fresh autopilot heartbeat, firmware 4.6.3, telemetry
and all 1166 reported parameters on `/dev/ttyU0`. Application configuration,
device data and protocol tooling remain outside the OS sources. Serial
nodes already present in `/dev` are not themselves device-detection evidence.

The operator subsequently confirmed a voice application's complete spoken
request, fresh USB reading and audible response about firmware and parameter
count. Its runtime reported all 1166 parameters and a server result 21.3 seconds
after speech. This is one spoken question, not general dialogue latency or
sustained operation validation; application credentials remain outside Git.

The complete 32 MiB boot wedge was backed up before deployment. The staged
container changed the kernel prefix while retaining the original ramdisk,
DTB payload and remaining wedge suffix. Full readback matched SHA-256
`a3a5dbc0aee395f2638a33632e7f4f190293080937a69072af3652ca1cf5491a`.
Ethernet/SSH, MCU keepalive and the upright Xorg session were retained.

This validates one hub and one CDC serial device. Other USB classes,
USB-C peripheral/OTG operation, suspend/resume, arbitrary device replacement
and sustained transfer stability remain unverified.

# YS-M33 U-Boot second-stage RAM probe

Origin: EmberBSD - physical probe receipt recorded by Codex (GPT-6).

Date: 2026-10-08. First YS-M33 tablet, Allwinner A133, 1 GiB DDR4 at
744 MHz, 32 GB eMMC. DC power, UART, USB-C and wired Ethernet were connected.
Board and panel assembly revisions are not recorded.

## Scope and inputs

This is a disposable feasibility probe, not an installed replacement loader.
Vendor secure boot0, BL31, OP-TEE, U-Boot and DRAM/display initialization
were retained. The probe was downloaded over vendor fastboot into RAM and
executed through an Android boot container. The U-Boot code has no storage
driver and wrote no boot or loader environment. It did not build or execute SPL.

Upstream: U-Boot v2026.10, commit
`5508406582f6f7120dce0c4b3059819a41788db2`, exported independently of an
older modified development checkout. Host tools: GCC 16.2.0,
Binutils 2.47.20260726, GNU make 4.4.1, Apple host clang and dtc on macOS.
The upstream `NO_PYTHON=1` option was used for the `u-boot.bin` target.

The experimental profile bypassed destructive RAM sizing, SPL-header boot
source detection and low-level GIC initialization. It advertised only the
lower 512 MiB and enabled the ARM64 Image header, position-independent entry,
relative initial stack and an 8 MiB heap. Autoboot was disabled. Environment
storage was NOWHERE; MMC, networking, USB, video and saveenv were disabled.

Liontron's control DT supplied the SoC/UART description, so the banner named
Liontron H-A133L. That is not identification or full support of this tablet.
Its inherited LPDDR4 configuration values were unused: no SPL or DRAM
initialization code was executed. This is not a YS-M33 DDR4 initialization recipe.
The patched source, defconfig and build outputs were retained locally as
experimental inputs; they are not a published board firmware build workflow.

## Physical observations

The first non-position-independent image aborted after UART initialization.
The linked function pointer was at `0x402171c8`, while the loader executed
the Image at `0x40080000`; its return address was in the actual loaded range.
The resulting 0x180000 displacement demonstrated the address mismatch.
PSCI reset did not recover that probe; the operator power-cycled the tablet.

With position-independent entry, the second image reached `ember-ram=>`
at 19:00:15 Moscow time. `version`, `bdinfo`, `help bootm`, FDT inspection
and bounded MMIO reads completed. Reported relocation was `0x5ffa7000`,
control FDT `0x5f7a0690`, UART `0x05000000`, and RAM size 512 MiB.

At 19:06:54, setting the inspected SoC watchdog system-reset configuration
and enable registers (`0x030090b4=1`, `0x030090b8=1`) returned to the
vendor chain without another operator action. Ordinary eMMC boot restored
EmberBSD, wired SSH, Xorg, awesomeWM and MCU keepalive.

## Bounded kernel handoff

A later RAM trial at 20:54:24 Moscow time used the same U-Boot binary to
enter the installed `EMBER64_A133_AUDIO #5` kernel through `booti`.
The unchanged native Image was appended after the complete probe container,
copied from `0x52052800` to `0x46000000`, and checked in hardware:
CRC32 `59ce640a`, 16990052 bytes. U-Boot relocated it to `0x40200000`.

| Additional artifact | SHA256 |
| --- | --- |
| Installed native kernel Image | `e954703573604764abf4e663be3ef8422472706a8ec897d281d100220ef2e2c7` |
| Combined RAM container, 17327972 bytes | `9be697c33938d3e0af5e859b7593200f62d7ba29eab5c3746463c96bc9e8ee8b` |

The full vendor runtime FDT at `0x44000000` was retained in place, resized,
and passed with `skip_board_fixup=1` and `fdt_high=ffffffffffffffff`.
The kernel attached all four CPUs, audio0 and genfb at `0x7bf46100`,
selected the FFS root on dk16 at 20:54:33, and started ordinary rc services
including MCU keepalive. It reported 478 MiB in this limited RAM profile;
ordinary boot still reports 986 MiB. The `single` boot argument did not
prevent multi-user rc startup; this was not a read-only or single-user trial.

The kernel free-memory log excluded `0x48000000` through `0x49000000`.
An overlapping vendor memreserve entry caused an LMB reservation warning;
complete secure-memory accounting remains unproven. The inherited framebuffer
was above the advertised lower RAM bank. This trial did not validate its
long-term ownership or start the graphical session through the probe.

A 16-second SoC watchdog was armed before kernel entry. At 20:54:39 it
returned to the vendor chain without operator intervention. Ordinary boot
restored SSH, Xorg, awesomeWM and MCU keepalive. Full boot and 128 KiB
environment readbacks were unchanged. No boot or environment writes occurred.

## Remaining acceptance

The probe did not read the kernel from eMMC, provide direct USB recovery,
initialize the display or independently service MCU7502. The lower RAM bank still contains vendor
secure firmware; its entire extent is not safe for allocation or memory tests.
Complete reserved-memory exclusion and secure-service handoff remain untested.
There was no persistent own-loader installation or secure-boot policy change.

Before installing a second stage, create a versioned YS-M33 profile with
explicit memory reservations, retained framebuffer and MCU handling. Validate
sustained kernel operation and a direct return to signed USB recovery in RAM first.
Full boot0/TOC1 replacement requires a separately proven authenticated
loading and recovery path; unsigned second-stage execution does not prove it.
